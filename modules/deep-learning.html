Frame the question

Deep learning starts with a decision, not a network. You first describe the real task in a way that can be demonstrated with examples and measured with evidence.

A vague goal such as “recognise animals” leaves too many questions unanswered. Should the model find every animal, draw a box around it, or choose one label? Clear boundaries determine the data you need, the output layer you build, and the mistakes you measure.

  1. 1

    Write down one realistic input and the exact output you want back.

  2. 2

    Name the task: classification, regression, detection, segmentation, sequence prediction, or generation.

  3. 3

    Choose success measures that reflect the real cost of mistakes—not simply the easiest score to calculate.

Picture it: Imagine writing an exam rubric before teaching the course. The rubric decides what counts as a correct answer.

For our animal example, one image goes in and three probabilities come out. The largest probability becomes the predicted class.

Build the evidence

A dataset is the model’s entire experience of the world. It will use any regular pattern that helps, whether that pattern expresses the true idea or an accidental shortcut.

If every dog is photographed on grass and every cat is photographed on a sofa, “background” becomes an easier clue than “animal.” The model can score well in the lab and fail immediately in a real home, park, shelter, or veterinary clinic.

  1. 1

    Collect variation in lighting, background, angle, distance, appearance, position, and image quality.

  2. 2

    Inspect examples by class and source; look for rare classes, duplicate files, broken records, and inconsistent labels.

  3. 3

    Ask what unrelated clue could reveal the answer. Then deliberately collect counterexamples that break that shortcut.

Picture it: A child shown only red apples may decide that “apple” means “red.” Variation teaches which features stay true when the scenery changes.

More examples help only when they add useful coverage. Ten thousand copies of the same narrow situation are still narrow data.

Protect the experiment

To know whether a model can handle new cases, some examples must remain outside the learning process. Each split has one job and should not quietly take on another.

When the model—or the people tuning it—repeatedly sees the final test answers, the score stops measuring generalisation. Duplicate images, the same patient in two splits, or future data leaking into the past can create confidence without real ability.

  1. 1

    Use training data to update weights and validation data to compare choices, tune settings, and decide when to stop.

  2. 2

    Seal the test set until the architecture and meaningful choices are fixed, then use it once for the final estimate.

  3. 3

    Keep related people, videos, devices, or time periods together, and learn preprocessing statistics from training data only.

Picture it: Training is the textbook, validation is the practice exam, and testing is the sealed final. Copying a question between them breaks the exam.

A 70/15/15 split is only an example. The important idea is separation; the right percentages depend on dataset size and structure.

Translate the world

A network cannot receive “a dog,” “a sentence,” or “a melody” directly. It receives a tensor: an organised block of numbers whose shape preserves useful structure.

The representation determines what relationships are easy to learn. Images need nearby pixels to stay nearby, text needs token order, and audio needs precise changes through time. Preprocessing is therefore part of the model’s language, not mere housekeeping.

  1. 1

    Images become rows and columns of pixel intensities, usually with red, green, and blue channels.

  2. 2

    A tokeniser breaks text into reusable pieces—sometimes a whole word, punctuation mark, or word fragment. Each piece receives an integer ID from a fixed vocabulary.

  3. 3

    An embedding table replaces each token ID with a learned vector. Audio is sampled into amplitude numbers; a spectrogram then summarises which frequencies are strong in each short time window.

Picture it: Think of representation as translation. The language changes from pictures or words to numbers, but the useful grammar—space, order, or time—must survive.

The same resize, tokeniser, vocabulary, sample rate, and normalisation must be used during training and real use. Changing them changes what the numbers mean.

Image · position becomes tensor shape

  1. 1

    Resize or crop the image to a known height and width.

  2. 2

    Turn each pixel channel into a number, often scaled to a small common range.

  3. 3

    Keep the row, column, and colour-channel axes so nearby pixels remain neighbours.

Picture it: A 224 × 224 × 3 tensor is a numbered colour grid: height, width, and three colour channels.

Meet the smallest learner

One artificial neuron is a small decision-maker. It combines several signals into one new signal that later neurons can use.

The neuron matters because the whole network is built from this repeatable operation. The complexity comes from learning many useful combinations and stacking them, not from one magical component.

  1. 1

    Multiply every input by a weight. A large positive weight strengthens a clue; a negative weight can argue against it.

  2. 2

    Add a bias, which shifts how much total evidence is needed before the neuron responds.

  3. 3

    Apply an activation such as ReLU. This non-linearity lets layers combine into curved, flexible decision boundaries.

Picture it: Picture a sound-mixing desk. Each input has a volume slider, the bias sets the baseline, and the activation decides what signal leaves the desk.

Stack useful transformations

A deep network turns the same example into a sequence of increasingly useful descriptions. Each layer receives the previous layer’s features and composes them into larger ideas.

Raw pixels are a poor language for “dog.” Edges are more useful; groups of edges can describe fur or curves; those patterns can form ears, eyes, and snouts. Hierarchy lets the model reuse simple discoveries to build complex ones.

  1. 1

    Early layers respond to local changes such as edges, colour transitions, or short sound patterns.

  2. 2

    Middle layers combine repeated local clues into textures, shapes, or meaningful phrase fragments.

  3. 3

    Later layers gather evidence across a wider area and make features useful for the final task.

Picture it: It is like looking through a stack of tracing sheets. Each sheet redraws the scene using the patterns that matter at its level.

The feature names are a helpful simplification, not rules written by a programmer. Training discovers the filters that reduce the loss.

The correction cycle

Learning is a repeated correction loop. Forward pass → loss → backpropagation computes gradients → optimiser updates weights. The network makes predictions, measures error, computes how the loss changes with each weight, and uses those gradients to adjust the weights.

A loss number alone says only “this was wrong.” Backpropagation turns that complaint into useful directions for millions of parameters, so an optimiser can use the loss gradients to update the weights.

  1. 1

    Forward propagation moves a batch through the layers and produces predictions.

  2. 2

    A loss function compares predictions with the correct answers; backpropagation calculates gradients from output to input.

  3. 3

    An optimiser uses those gradients to update the weights. The learning rate controls how large each step is.

Picture it: Imagine descending a foggy hill. The gradient tells you which way slopes downward; the learning rate decides whether you take careful steps or dangerous leaps.

One update teaches very little. Useful behaviour emerges from many batches of examples providing many small, partly noisy corrections.

Quick check · Is backpropagation itself the learning-rate rule?

No. It computes gradients used by an optimizer.

Train with discipline

Training must continue long enough to discover stable patterns, but not so blindly that the model memorises quirks of the training set.

Training loss almost always rewards more training. Validation data asks the more important question: are these improvements useful on examples that did not update the weights?

  1. 1

    Train on small batches; one pass through every training example is an epoch. Switch to evaluation mode before validation.

  2. 2

    Plot training and validation curves together. High values for both suggest underfitting; a widening gap suggests overfitting.

  3. 3

    Use augmentation, weight decay, dropout, a simpler model, or early stopping—and save the best validation checkpoint.

Picture it: One coach watches practice; another watches an unseen match. If practice keeps improving while match performance worsens, the player is learning the drill rather than the game.

Hyperparameters such as learning rate, batch size, depth, and dropout are chosen with validation evidence. They are not learned like ordinary weights.

Match shape to problem

An architecture is a set of useful assumptions about how information is organised. The right design makes important patterns easier and cheaper to learn.

Images contain many local patterns, not one universal feature. Sequences need memory or direct links across time. Architecture decides how information is shared, how far context can travel, and what the model can compute efficiently.

  1. 1

    A CNN layer learns many filters. Every filter scans every image, producing its own feature map. Training changes the filter values; testing reuses the learned filters without inventing new ones.

  2. 2

    An RNN reads one item at a time and updates a hidden state—a fixed-length vector that compresses what it has seen. That state can produce scores for the next word or another sequence output.

  3. 3

    A Transformer creates a query, key, and value for every token. Query–key matches become attention weights, which gather useful values into context. Training rewards links that help reduce prediction error.

Picture it: Choose a tool shaped like the material: a movable stencil for space, a notebook passed through time, or a web of spotlights for attention.

Choose with evidence, not fashion. CNNs remain natural for spatial data. RNNs can suit compact streaming systems. Transformers usually handle long context and parallel training better, but standard attention can require much more memory as a sequence grows.

CNN · a bank of reusable spatial detectors

  1. 1

    A layer learns many filters—not only one. Early filters may respond to different edges, colours, or textures.

  2. 2

    Every learned filter scans every training image and every test image. One filter produces one feature map showing where its pattern responded.

  3. 3

    Training adjusts all filter values. At test time those values are frozen and reused; the model does not design a special filter for each new picture.

  4. 4

    Later layers combine the stack of feature maps into more complex evidence such as curves, parts, or whole objects.

Picture it: Picture a case of many reusable stencils. Every stencil is swept across every picture, producing its own map of matches.

When to choose it: Choose a CNN when locality and spatial reuse matter—images, video frames, grids, or compact vision systems. CNN ideas are also often combined with attention.

Reuse useful experience

Transfer learning starts from a model that has already learned general patterns from a large dataset, then adapts that knowledge to your narrower task.

Training a large network from random weights can require enormous amounts of labelled data and computation. Useful early features—edges, textures, shapes, language patterns—often transfer between related tasks.

  1. 1

    Replace the old output head with one that matches the new classes or target.

  2. 2

    First freeze the pretrained backbone and train only the new head; this tests the existing features cheaply.

  3. 3

    If needed, unfreeze some layers and fine-tune gently with a smaller learning rate so useful knowledge is not destroyed.

Picture it: A trained carpenter does not relearn how to measure and cut wood for every new table. They reuse general craft and learn the new design.

Transfer works best when the earlier data and new task share useful structure. A model can also transfer unwanted biases, so evaluation still matters.

Earn confidence

Evaluation asks not only “how often is it right?” but “where, for whom, and with what confidence does it fail?” The final test set estimates performance on actually unseen data.

A model can reach 95% accuracy by always predicting the common class in an imbalanced dataset. In medicine, fraud, or safety, one missed positive can matter far more than one false alarm.

  1. 1

    Evaluate the selected checkpoint once on the untouched test set and report class-level precision, recall, F1, and support.

  2. 2

    Read the confusion matrix and inspect individual errors for bad labels, rare conditions, occlusion, or shortcut patterns.

  3. 3

    Check calibration, uncertainty, and subgroup performance. Choose decision thresholds on validation data using real-world costs.

Picture it: Accuracy is the final grade; the confusion matrix is the marked paper showing which questions were misunderstood.

Lower thresholds usually find more true positives but create more false alarms. Higher thresholds usually do the opposite.

Move beyond the notebook

A deployed model is not only a weights file. It is a complete, repeatable route from raw input to a decision that behaves the same way outside the training notebook.

A brilliant model can produce nonsense if the live system resizes differently, swaps class order, forgets normalisation, or leaves dropout active. Failures can occur at the interfaces around the network.

  1. 1

    Save the architecture, weights, class order, dimensions, normalisation, tokeniser, threshold, software versions, and configuration.

  2. 2

    Validate the input, apply the same preprocessing, switch to evaluation mode, disable gradients, predict, and decode the result.

  3. 3

    Test the complete pipeline in its target environment for latency, memory, privacy, energy use, throughput, and failure handling.

Picture it: Treat deployment like sealing a recipe with its ingredients, measurements, oven settings, and serving rule—not saving only the cake tin.

The same pipeline may run on a phone, API, browser, hospital system, edge device, or cloud GPU. The constraints can change which model is best.
